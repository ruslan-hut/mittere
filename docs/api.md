# Mittere API

Базовый адрес: `http://{bind_ip}:{port}` (по умолчанию `http://127.0.0.1:9800`).

Версия 2. Сервис рассылает уведомления в Telegram по **темам**: отправитель
указывает тему, сервис находит привязанные к ней **каналы** (личный чат, группа
или тема форума) и отправляет в каждый, после чего отвечает тем, что
действительно произошло.

## Что изменилось по сравнению с v1

| v1 | v2 |
|---|---|
| одна коллекция `subscriptions`, где подписчик, получатель и отправитель — один `User` | `channels`, `topics`, `subscriptions` (тема ↔ канал), `senders` |
| маршрутизация по роли `admin`/`user` или по username | маршрутизация по теме; личный чат — такой же канал |
| только личные чаты | личные чаты, группы и темы форумов (`message_thread_id`) |
| `200 OK` до фактической отправки | ответ после отправки, с результатом по каждому получателю |
| один `auth_token` даёт всё | токен `send` (только отправка) и токен `admin` (управление) |
| нет журнала | коллекция `events` с историей доставки, TTL 90 дней |
| `/users/` | `/senders/` (отправители) и `/channels/` (получатели) |

Миграция выполняется при первом запуске: документы v1 копируются в
`users_v1`, каждый подписчик с Telegram ID становится личным каналом, его
`subscription_type` — темой, подписчики дополнительно подписываются на тему
`default` (а администраторы и на `admin`), пользователи с токеном становятся
отправителями. Старый `POST /tg/msg` продолжает работать.

## Аутентификация

Все запросы, кроме `GET /health`, требуют заголовок:

```
Authorization: Bearer <token>
```

Токены трёх уровней:

| Уровень | Откуда | Что можно |
|---|---|---|
| `admin` | `auth_token` из конфигурации или отправитель со `scope: admin` | всё |
| `send` | отправитель со `scope: send` | только `POST /messages`, `POST /tg/msg`, `GET /tg/test`, и только по темам из `allowed_topics` (пустой список — любая тема) |
| `agent` | отправитель со `scope: agent` | только журнал (`/events`) по темам из `allowed_topics`: чтение, разбор, удаление сообщений. Пустой список — ни одной темы. Публиковать не может |

Запрос с токеном `send` к управляющим ручкам и к журналу получает `403`; с
токеном `agent` — к публикации, темам, каналам, отправителям, а также к событию
чужой темы.

## Формат ответа

```json
{
  "data": {},
  "success": true,
  "status_message": "Success",
  "timestamp": "2026-11-13T10:30:00Z"
}
```

При ошибке `success: false`, причина — в `status_message`; у неудачной отправки
в `data` всё равно лежит событие с разбором по получателям.

## Отправка сообщений

### POST /messages

Отправляет сообщение в тему. Ответ приходит **после** того, как сервис попытался
доставить его каждому получателю.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `topic` | string | нет | код темы, например `marketing.shipments`; без темы — `default` |
| `type` | string | да | категория события (`alert`, `notification`, `report`) |
| `subject` | string | нет | подзаголовок; если пусто, выводится код темы |
| `text` | string | нет | текст сообщения |
| `payload` | any | нет | произвольные данные, выводятся блоком кода |
| `dedup_key` | string | нет | ключ повтора: при повторной отправке с тем же ключом сервис дошлёт только тем, кто не получил |

Код темы — слова в нижнем регистре, разделённые `.`, `_` или `-`.

**Коды ответа** — главное, на что смотрит вызывающая сторона:

| Код | Что значит |
|---|---|
| `200` | доставлено всем получателям |
| `207` | доставлено части получателей (разбор — в `data.deliveries`) |
| `409` | в теме нет активных каналов, либо это же сообщение (`dedup_key`) прямо сейчас отправляет другой вызов |
| `502` | не доставлено никому |
| `404` | тема неизвестна |
| `403` | тема не разрешена этому токену |
| `400` | не удалось разобрать запрос |

1С помечает уведомление доставленным по `200`, поэтому всё, что не доставлено
полностью, отвечает не-`200`, и уведомление уйдёт в следующий цикл отправки.
Чтобы повтор не задвоил сообщения у тех, кто их уже получил, передавайте
`dedup_key` (например, хэш содержимого из `InformationRegister.Notifications`).
Пока сообщение с этим ключом отправляется, повторный вызов получает `409` и
ничего не отправляет; если первый вызов оборвался, его захват истекает (3
минуты) и повтор продолжает с того места, где тот остановился. Журнал
пишется после каждого получателя, поэтому перезапуск сервиса в середине
веера не приводит к повторной отправке тем, кто уже получил.

**Пример:**

```bash
curl -X POST http://127.0.0.1:9800/messages \
  -H "Authorization: Bearer <send-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "topic": "marketing.shipments",
    "type": "alert",
    "text": "Накладна 42: прострочено 3 дні",
    "payload": {"doc": "42", "days": 3},
    "dedup_key": "shipment-42-2026-11-13"
  }'
```

**Ответ (`207`, одному из двух получателей не дошло):**

```json
{
  "data": {
    "event_id": "9f1c2b3a4d5e6f7a8b9c0d1e",
    "topic": "marketing.shipments",
    "type": "alert",
    "status": "partial",
    "created_at": "2026-11-13T10:30:00Z",
    "finished_at": "2026-11-13T10:30:01Z",
    "deliveries": [
      {
        "channel_id": "-1001234567890",
        "chat_id": -1001234567890,
        "status": "sent",
        "attempts": 1,
        "message_id": 345,
        "sent_at": "2026-11-13T10:30:01Z"
      },
      {
        "channel_id": "-1009876543210",
        "chat_id": -1009876543210,
        "status": "failed",
        "attempts": 2,
        "error": "bot is not a member of the chat"
      }
    ]
  },
  "success": false,
  "status_message": "Delivered to some recipients only",
  "timestamp": "2026-11-13T10:30:01Z"
}
```

Статусы события: `delivered`, `partial`, `failed`, `no_recipients`, `pending`.
Статусы доставки: `sent`, `failed`, `pending`, `retracted` (удалено из чата, см. `retract`).

Ответ Telegram `429` обрабатывается: сервис выжидает `retry_after` и повторяет
отправку один раз; кроме того, на каждый чат действует ограничение (по
умолчанию 20 сообщений в минуту, `telegram.rate_limit` и `telegram.rate_window`).
Повторно, уже без разметки, отправляется только то, что Telegram отверг из-за
разметки; «бот заблокирован», «чат не найден» и сетевые сбои считаются
окончательными и попадают в журнал как есть.

### POST /tg/msg — устаревший

Оставлен, чтобы существующие рассылки 1С не отвалились. Тело — как в v1
(`type`, `subject`, `role`, `username`, `text`, `payload`), дополнительно
принимает `topic` и `dedup_key`. Маршрутизация:

- без `topic` и без `role` — тема `default`;
- `role: admin` — тема `admin`;
- `username` — доставка в каналы этого Telegram-пользователя, независимо от темы.

Коды ответа — те же, что у `POST /messages`.

### GET /tg/test — устаревший

Отправляет тестовое сообщение в тему `default` или в тему из параметра
`?topic=`.

## Темы

Управление темами, уровень `admin`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/topics` | список тем |
| POST | `/topics` | создать тему |
| GET | `/topics/{code}` | одна тема |
| PUT | `/topics/{code}` | изменить название и описание |
| DELETE | `/topics/{code}` | удалить тему и её подписки |

Поля темы: `code` (обяз.), `title`, `description`, `bot` (на будущее, для
рассылки разными ботами). Темы `default` и `admin` удалить нельзя.

В ответе на чтение темы есть `channels` - число **активных** каналов, которые на
неё подписаны: столько получателей увидят сообщение. Поле только на чтение, в
теле запроса не принимается. Ноль означает, что отправка в тему вернёт `409`.

```bash
curl -X POST http://127.0.0.1:9800/topics \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"code": "marketing.shipments", "title": "Маркетингові відправки"}'
```

## Каналы

Канал — чат, куда идёт доставка: личный чат (`private`), группа (`group`) или
тема форума (`forum`). Идентификатор канала — `chat_id`, а для темы форума
`chat_id:thread_id`. Уровень `admin`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/channels` | список каналов с их темами |
| POST | `/channels/link` | выдать код привязки |
| GET | `/channels/{id}` | один канал |
| PUT | `/channels/{id}` | изменить `state`, `title`, список `topics` |
| DELETE | `/channels/{id}` | удалить канал и его подписки |

Поля канала: `channel_id`, `chat_id`, `thread_id`, `kind`, `title`, `username`,
`state` (`active`, `await`, `disabled`), `linked_at`, `linked_by` и
`linked_by_id` (кто привязал чат — он же может остановить доставку командой
`stop` в группе), `topics`.

`PUT` принимает `state`, `title` и `topics`; `chat_id` и `thread_id` задаются
при привязке чата и руками не меняются. Темы и состояние проверяются до
записи: если в списке неизвестная тема, не меняется ничего.

### Привязка чата кодом

`chat_id` руками нигде не вводится. Порядок такой:

1. `POST /channels/link` с телом `{"topic": "marketing.shipments"}` (тему можно
   не указывать) — в ответе код и срок его действия:

```json
{
  "data": {
    "code": "N9PE-RYQG",
    "topic": "marketing.shipments",
    "created_at": "2026-11-13T10:30:00Z",
    "expires_at": "2026-11-13T11:00:00Z"
  },
  "success": true
}
```

2. Бот добавляется в нужный чат, и в этом чате ему отправляют команду:

```
/link@имя_бота N9PE-RYQG
```

В теме форума команду отправляют прямо в этой теме — тогда каналом становится
именно она. В личном чате достаточно отправить сам код сообщением или
`/start N9PE-RYQG`.

3. Сервис запоминает `chat_id` и `thread_id` из этого сообщения, делает канал
   активным и подписывает его на тему из кода. Код одноразовый и сгорает через
   `link.code_ttl_minutes` (по умолчанию 30 минут).

Так обходится privacy mode: боту в группе видны только адресованные ему команды,
и ничего, кроме них, читать не требуется.

### Команды бота

| Команда | Где | Что делает |
|---|---|---|
| `/link КОД` | группа, форум, личный чат | привязывает чат к теме из кода |
| `/start` | личный чат | регистрирует чат, ждёт кода |
| `/start КОД` | личный чат | то же, что `/link` |
| `/status` | везде | показывает канал, его состояние и темы |

| `/stop` | личный чат — владелец, группа — тот, кто привязал чат | выключает доставку в этот чат (подписки сохраняются) |
| `/test` | везде | отвечает тестовым сообщением |

## Отправители

Клиенты API: токен и темы, в которые ему можно писать. Уровень `admin`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/senders` | список (токены скрыты) |
| POST | `/senders` | создать; токен возвращается один раз, при создании |
| GET | `/senders/{username}` | один отправитель (токен скрыт) |
| PUT | `/senders/{username}` | изменить |
| DELETE | `/senders/{username}` | удалить |

Поля: `username` (обяз.), `name`, `token` (если не задан — сервис сгенерирует),
`scope` (`send` по умолчанию, `agent` или `admin`), `allowed_topics` (для `send`
пустой список — любая тема, для `agent` — ни одной), `state` (`active`, `disabled`).

`PUT` меняет только то, что передано: поле, которого нет в теле, сохраняет
прежнее значение. Так обновление без `allowed_topics` не открывает отправителю
все темы, а без `state` не включает обратно выключенного.

```bash
curl -X POST http://127.0.0.1:9800/senders \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"username": "1c", "scope": "send", "allowed_topics": ["marketing.shipments"]}'
```

## Журнал

Уровень `admin` — весь журнал; `agent` — только события тем из его
`allowed_topics`, событие чужой темы отвечает `403`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/events` | список событий, новые первыми |
| GET | `/events/{id}` | одно событие с разбором доставки |
| POST | `/events/{id}/triage` | вердикт по событию |
| POST | `/events/{id}/retract` | удалить сообщения события из чатов |
| POST | `/events/resolve` | итог по задаче в чаты, затем удалить её события |

Параметры `/events`: `topic`, `status`, `from`, `to` (RFC 3339 или `ГГГГ-ММ-ДД`),
`limit` (по умолчанию 100, максимум 500), `triaged` (`true` / `false`), `after`
(`event_id` курсора), `task_key` (только события с `triage.task_key`, равным
ему, — вместе с итогом, если задача уже закрыта через `resolve`). С `after` или `triaged` события идут по возрастанию
`created_at`, старые первыми; `after` отдаёт только созданные после курсора
(в одну и ту же миллисекунду — по `event_id`). Неизвестный курсор — `400`.
Агент без `topic` получает все свои темы, с чужой `topic` — `403`.

```bash
curl -H "Authorization: Bearer <admin-token>" \
  "http://127.0.0.1:9800/events?topic=marketing.shipments&status=failed&from=2026-11-01"
```

Лента агента — `?triaged=false`: старые неразобранные первыми; разобранное из
неё уходит само, поэтому основной цикл курсора не требует. `after` нужен, чтобы
пролистать страницу событий, которые агент оставил без вердикта:
`?triaged=false&after=<event_id последнего полученного>`. Событие, которое ещё
доставляется, может появиться в журнале чуть позже соседнего с более поздним
`created_at`, поэтому один `after` без `triaged=false` его может пропустить. Если
событие-курсор удалено TTL (старше 90 дней), ответ `400` — начните без `after`.

```bash
curl -H "Authorization: Bearer <agent-token>" \
  "http://127.0.0.1:9800/events?triaged=false&after=6740c1e2a9b3f0d4e5a6b7c8&limit=50"
```

### POST /events/{id}/triage

```json
{"verdict": "task", "task_key": "T44d6a120", "note": "новая ошибка проведения"}
```

`verdict` — `task`, `duplicate` или `noise` (иначе `400`); `task_key` и `note`
необязательны. В событие пишется `triage: {verdict, task_key, note, by, at}`, где
`by` — отправитель токена. Повтор перезаписывает прежний вердикт. Ответ —
событие целиком.

### POST /events/{id}/retract

```json
{"reason": "дубль T44d6a120"}
```

`reason` обязателен. Каждое сообщение события со статусом доставки `sent` и
`message_id` удаляется (`deleteMessage`); удалённое получает статус `retracted`.
Если Telegram отказал (сообщение старше 48 часов, у бота нет права удалять),
доставка остаётся `sent`, а в `error` пишется причина с префиксом `retract:`.
Сообщение, которое уже удалили руками, считается удалённым. В событии
сохраняется `retraction: {reason, by, at}`.

Повтор безопасен: удалённое не трогается, отказанное пробуется ещё раз;
`retraction` остаётся от первого вызова. Пока идёт удаление, событие занято:
второй `retract` и повтор публикации из 1С с тем же `dedup_key` получают `409`.
Поле `status` события остаётся итогом доставки и после удаления не меняется. Ответ —
событие целиком: `200`, если ни одного сообщения в чатах не осталось, `207`, если
Telegram что-то не удалил. Событие, которое ещё доставляется, отвечает `409` (как
и `triage`). Повтор публикации с тем же `dedup_key` после удаления сообщение
обратно не отправляет.

Чтобы удалять, бот должен быть **администратором** чата с правом «Удаление
сообщений» (Delete messages). Без него каждая доставка вернётся с ошибкой
`retract: … message can't be deleted …`, а ответ будет `207`. В личном чате бот
может удалять свои сообщения без прав.

### POST /events/resolve

```json
{"task_key": "T44d6a120", "text": "исправлено, документ перепроведён", "subject": "необязательно"}
```

Закрывает в чатах задачу, к которой события привязаны вердиктом
(`triage.task_key`). `task_key` и `text` обязательны (иначе `400`); `subject` по
умолчанию — `task_key`. Агент видит только события своих тем.

1. Берутся события задачи (до 500, кроме самого итога). Нет ни одного — `404`;
   какое-то сейчас доставляется или удаляется — `409`.
2. Итог уходит **новым сообщением** (тип `resolved`) в конец ленты — по одному
   в каждый канал (чат или тему форума), куда дошло хотя бы одно событие задачи,
   включая уже удалённые. Старые сообщения не правятся.
3. Только когда итог дошёл во все эти каналы, события задачи удаляются из чатов
   так же, как `retract` (причина `resolved <task_key>`), и в каждое пишется
   `resolution: {task_key, result_id, by, at}`, где `result_id` — `event_id`
   итога. Если итог куда-то не дошёл, события не трогаются: ни один чат не
   остаётся без тревоги и без итога.

Итог — отдельное событие журнала с `resolves: <task_key>`, `dedup_key:
resolve:<task_key>` и вердиктом `task` на ту же задачу, поэтому в ленту
`triaged=false` он не попадает, а в `?task_key=` виден.

Повтор безопасен: итог досылается только туда, куда не дошёл (с `text` повтора;
уже отправленное не меняется, а дошедший всюду итог не шлётся снова), удалённое не
трогается, отказанное Telegram удаление пробуется ещё раз, `resolution` остаётся
от первого вызова.

Ответ:

```json
{"data": {"task_key": "T44d6a120", "result": {…событие итога…}, "events": [{…}, …]}, "success": true}
```

`200` — итог во всех каналах и ни одного сообщения событий задачи в чатах не
осталось; `207` — что-то не доделано (итог дошёл не всюду или Telegram не дал
удалить), `data` тот же, повтор доделает.

События хранятся 90 дней (`events.ttl_days`), дальше удаляются TTL-индексом.

## Состояние

### GET /health

Без токена — краткое состояние (для мониторинга), с токеном `admin` —
дополнительно счётчики и последние ошибки доставки. Отвечает `503`, когда
состояние не `ok`.

```json
{
  "data": {
    "status": "ok",
    "uptime": "72h13m5s",
    "bot": "mittere_bot",
    "bot_alive": true,
    "database": "ok",
    "channels": 12,
    "topics": 5,
    "failures_24h": 0
  },
  "success": true
}
```

---

## Коды ошибок

| Код | Значение |
|---|---|
| 200 | успех |
| 201 | создано |
| 207 | доставлено части получателей, либо удалено не всё (`retract`), либо задача закрыта не до конца (`resolve`) |
| 400 | неверный запрос |
| 401 | нет токена или токен неизвестен |
| 403 | не хватает прав: нужен `admin` (или `agent` для журнала), либо тема не разрешена токену |
| 404 | не найдено (тема, канал, отправитель, событие) |
| 409 | в теме нет активных каналов, либо сообщение уже отправляется, либо запись с таким ключом существует, либо событие ещё доставляется (`triage`, `retract`, `resolve`) |
| 500 | внутренняя ошибка |
| 502 | не доставлено никому |
| 503 | сервис не в порядке (`/health`) |
